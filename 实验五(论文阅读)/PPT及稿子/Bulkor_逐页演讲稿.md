# Bulkor 逐页演讲稿

建议总时长：10 到 12 分钟。  
使用方式：录制前不需要逐字背诵，但每页的“核心句”和“过渡句”建议尽量保持一致，这样整场汇报的逻辑会更稳定。

## 第 1 页：标题页

建议时间：40 秒

核心句：这篇论文研究的是 Path ORAM 的批量构建问题，也就是如何把已有的大量数据安全、高效地初始化成 ORAM 结构。

图示提示：标题页只作开场，不展开技术细节。

口播稿：

大家好，我是王旭。今天汇报的论文是 IEEE S&P 2024 的 Bulkor: Enabling Bulk Loading for Path ORAM。这篇论文属于数据安全和隐私保护方向，涉及 ORAM、TEE，以及访问模式保护。

我们平时说数据安全，最容易想到的是加密，也就是保护数据内容本身。但这篇论文关注的是另一个更隐蔽的问题：即使数据内容被加密，访问哪些位置、以什么顺序访问、访问频率如何，这些访问模式仍然可能泄漏隐私。Bulkor 研究的具体问题是：当系统已经有大量数据时，如何安全并且高效地把这些数据构建成 Path ORAM。

过渡句：接下来我先给出汇报路线，再逐步解释为什么这个问题重要。

## 第 2 页：汇报路线

建议时间：40 秒

核心句：本次汇报按照“背景、问题、方法、评价”四个层次展开。

图示提示：指向四个模块，说明听众接下来会听到什么。

口播稿：

这次汇报分成四部分。第一部分是背景，主要解释访问模式泄漏以及 Path ORAM 的基本思想。第二部分是问题，也就是在 TEE 场景下，为什么 ORAM bulk loading 本身会成为一个新的安全和性能问题。第三部分是方法，介绍 Bulkor 如何批量构建 ORAM，重点讲它为什么不是简单 shuffle，而是先随机分配 leaf label，再进行 oblivious 的布局调整。第四部分是评价，包括实验结果、论文贡献、不足，以及我自己的思考。

这四部分的关系是：先讲清楚为什么需要 ORAM，再讲清楚为什么需要 bulk loading，最后讲 Bulkor 如何解决这个问题。

过渡句：我们先从最基础的问题开始：只加密数据为什么还不够？

## 第 3 页：只加密数据为什么还不够

建议时间：60 秒

核心句：加密保护的是数据内容，但访问地址、访问顺序和访问频率仍然可能泄漏信息。

图示提示：左侧是 client，右侧是 cloud server；中间箭头表示请求，密文内容安全，但 access pattern 仍然可见。

口播稿：

这一页想说明的是：加密并不等于访问行为也安全。图中 client 访问云服务器上的加密数据，数据内容本身是密文，所以攻击者看不到明文。但是，如果服务器或者攻击者能观察到访问轨迹，就仍然可能看到访问了哪些地址、访问顺序是什么、某些地址是否被频繁访问。

举两个例子。在加密数据库里，如果系统频繁访问某些索引页，可能暴露查询条件；在云存储中，如果某个文件在特定时间被频繁访问，也可能暴露用户行为。也就是说，攻击者不一定需要看到明文，只要看到访问模式，就可能推断出敏感信息。

所以 ORAM 要解决的不是“内容加密”问题，而是“访问模式隐藏”问题。

过渡句：为了隐藏访问模式，下面引入 ORAM，特别是这篇论文基于的 Path ORAM。

## 第 4 页：ORAM 与 Path ORAM

建议时间：80 秒

核心句：Path ORAM 的核心不变量是：每个数据块要么在 stash 中，要么在它对应 leaf label 的 root-to-leaf 路径上。

图示提示：指向官方图中的 Position Map、Stash、Path Buffer 和 ORAM Tree，强调服务器端是一棵二叉树。

口播稿：

ORAM 的目标是让服务器看不出用户真实访问的是哪个数据块。而ORAM的一个最经典且广泛的实现就是 Path ORAM。

右侧的服务器存储是一棵二叉树，也就是 ORAM Tree。每个数据块会随机绑定一个 leaf label，也就是叶子标签。Path ORAM 要维持一个主不变量：一个数据块必须位于它对应 leaf label 从根到叶子的路径上，或者暂存在左侧 controller storage 里的 stash 中。

图中的 position map 记录逻辑地址到 leaf label 的映射。访问某个块时，控制器通过 position map 找到对应 leaf，然后读取整条 root-to-leaf path，而不是只读取单个位置。这样服务器看到的是一整条路径访问，而不是精确的数据块位置。

这篇论文后面所有 bulk loading 的正确性，都要围绕这个不变量展开：构建出来的 ORAM 状态必须与标准 Path ORAM 产生的状态相同。

过渡句：理解 Path ORAM 后，下一步要看它放到 TEE 场景里会带来什么新问题。

## 第 5 页：TEE 带来的机会与新问题

建议时间：70 秒

核心句：TEE 可以把 ORAM controller 放到服务器本地，但也引入 enclave 内部访问模式泄漏的问题。

图示提示：指向 Client、TEE Enclave、Untrusted Storage 三层，再指出外部观察点和内部侧信道观察点。

口播稿：

TEE，比如 Intel SGX，给 ORAM 带来一个机会：可以把 ORAM controller 放进服务器本地的 enclave 里。这样大量路径访问和处理都可以在服务器本地完成，减少客户端和服务器之间的网络通信。

但 TEE 不是万能的。它通常保护的是 enclave 中的数据值和计算完整性，但不一定完全隐藏 enclave 内部的访问模式。图里有两个观察点：第一个是外部观察，也就是不可信服务器看到 ORAM tree 的访问轨迹；第二个是内部侧信道，也就是 enclave 内部访问内存时可能被观察到的模式。

因此论文提出的 bulk loading 过程需要满足 doubly-oblivious：不仅 TEE 外部访问模式不能泄漏，TEE 内部算法执行时的访问模式也不能依赖敏感数据。

过渡句：在这样的背景下，论文正式研究的问题就是如何批量构建 ORAM。

## 第 6 页：本文问题：如何批量构建 ORAM

建议时间：70 秒

核心句：Bulk loading 的目标是把普通数据数组一次性构建为 ORAM tree、stash 和 position map。

图示提示：左边是逻辑地址和数据，右边是 ORAM tree；右侧补充输出包括 ORAM tree、stash、position map。

口播稿：

这页定义论文的问题：给定一批已有数据，包括数据块和它们的逻辑地址，目标是一次性构建出完整的 Path ORAM 状态。输出不仅是 ORAM tree，还包括 stash 和 position map。

最直接的做法是把数据逐条插入 ORAM。但这样很慢，因为每次插入都要做一次 Path ORAM 访问，整体复杂度会到 O(N log^3 N)。更重要的是，构建过程本身也不能泄漏访问模式，尤其在 TEE 场景下，内部访问模式也要 oblivious。

另外，最终输出分布必须和标准 Path ORAM 一致。也就是说，不能只是“看起来像一棵树”，而要保证 leaf label、数据块位置和 stash 状态都满足 Path ORAM 的安全分布。

过渡句：一个自然想法是先随机打乱数据再填进树里，但论文指出这个方法并不安全。

## 第 7 页：看似自然但错误的方案

建议时间：70 秒

核心句：随机打乱数据块不等于得到 Path ORAM 所需的独立随机 leaf label 分布。

图示提示：右侧官方图展示 physical address 和 leaf label 的关联；强调这是错误方案的反例。

口播稿：

这页讲一个看似自然但错误的方案。我们可能会想：先随机打乱所有数据块，然后直接填进 ORAM tree，最后根据物理位置反推出每个块的 leaf label。直觉上，既然已经 shuffle 了，好像位置也是随机的。

但问题在于，物理位置来自一个排列，不同数据块的位置并不是独立随机变量。再根据物理位置反推 leaf label，就会让 leaf label 之间产生相关性。而 Path ORAM 需要的是每个块独立随机分配 leaf label。

这种相关性可能导致后续访问轨迹被区分，也就是说攻击者可以统计地判断这是由简单 shuffle 构造出来的 ORAM，而不是标准 Path ORAM 的分布。所以论文强调：随机打乱不等于安全，关键是要先保证正确的随机分布。

过渡句：Bulkor 的核心思想正是反过来：先保证 leaf label 的安全分布，再解决物理布局。

## 第 8 页：Bulkor 的核心思想

建议时间：90 秒

核心句：Bulkor 先独立随机分配 leaf label，再用 oblivious 的方式调整 bucket 和物理地址。

图示提示：沿官方 pipeline 从左到右讲，不需要解释每个算法细节，只讲阶段作用。

口播稿：

这一页是 Bulkor 的整体流程。它的核心思想可以概括为一句话：先保证安全分布，再解决物理布局。

第一步是 Assign leaf，为每个真实数据块独立随机分配 leaf label。这一步保证了 Path ORAM 所需的 leaf label 分布。第二步是构建 position map，因为后续访问需要知道逻辑地址对应哪个 leaf label。第三步是调整 bucket ID，解决某些 bucket 可能 overflow 溢出的问题。第四步是分配物理地址，并用 oblivious placement 把数据放到对应位置。最后再填充 dummy blocks，让 ORAM tree 中没有真实块的位置也被假块填满。

这里的关键是，所有和敏感数据相关的排序、调整和放置，都要通过 oblivious sort、固定扫描、条件移动等方式完成，避免控制流和内存访问模式泄漏信息。

复杂度上，朴素逐条插入是 O(N log^3 N)，而 Bulkor 将理论复杂度降低到 O(N log^2 N)。

过渡句：在这个流程中，position map 和 bucket overflow 是两个比较关键的步骤，下面分别解释。

## 第 9 页：关键步骤一：递归构建 position map

建议时间：60 秒

核心句：position map 记录逻辑地址到 leaf label 的映射，但它本身可能太大，不能全部放在 enclave 中。

图示提示：先指左侧 position map 问题，再指右侧递归结构：Top map、ORAM for posmap、ORAM for data。

口播稿：

Path ORAM 需要 position map 来记录 logical address 到 leaf label 的映射。问题是，当数据规模很大时，position map 本身也会很大，TEE enclave 不一定能保存全部映射。

Bulkor 的做法是递归构建 position map。简单理解，就是把 position map 本身也当作数据，再放进一个更小的 ORAM 里；如果这个更小 ORAM 的 position map 仍然太大，就继续递归。最后只把最顶层的小 map 留在 enclave 中。

这种结构有点像多级索引：底层是真实数据，上层是访问底层所需的元数据。这样既能支持后续 ORAM 访问，也避免 enclave 内部存储压力过大。

过渡句：除了 position map，另一个关键问题是随机分配 leaf label 后可能出现 bucket overflow。

## 第 10 页：关键步骤二：解决 bucket overflow

建议时间：90 秒

核心句：Bulkor 允许块沿自己的 root-to-leaf 路径向父节点移动，从而解决 overflow，同时保持 Path ORAM 主不变量。

图示提示：先指左侧小树里的 overflow，再指红色上移箭头，最后指右侧安全要求。

口播稿：

当每个块独立随机分配 leaf label 后，某些叶子 bucket 可能会超过容量。比如图中 capacity 等于 2，但某个叶桶里有 a、b、c 三个块，就出现了 overflow。

Path ORAM 的主不变量要求块必须在自己的 root-to-leaf 路径上，或者在 stash 中。因此一个合法的调整方式是：如果叶桶满了，可以把其中某个块沿着自己的路径向父节点移动。只要它仍然在对应路径上，就不会破坏 Path ORAM 的正确性。

但这里还有安全要求：调整过程不能暴露哪个 bucket 溢出了，也不能让控制流依赖具体数据。Bulkor 使用固定扫描、occupancy counters 和 cmov 条件移动来完成调整。也就是说，即使算法内部在处理不同块，外部看到的访问模式和分支行为也尽量保持与敏感数据无关。

所以 OAdjustBucketID 的核心就是两件事同时满足：消除容量冲突，并且不让调整过程泄漏数据分布。

过渡句：方法讲完后，我们看它在系统实现和实验中是否真的带来性能收益。

## 第 11 页：实现与性能结果

建议时间：80 秒

核心句：Bulkor 不只是理论算法，它在 SGX + Rust 实现中相对基线取得了明显加速。

图示提示：左侧讲实现细节，右侧讲数字；柱状图只讲趋势，不逐个解释。

口播稿：

论文实现了一个 Intel SGX + Rust 的原型系统。为了满足 oblivious 要求，系统中使用 CMOV 实现条件移动，避免数据相关分支；加解密使用 AES-NI 加速；排序和 placement 等步骤也进行了多线程并行。

性能上，论文报告了明显加速。总体不同设置下，相比 Oblix 有 8.7 到 54.6 倍加速，相比 ZeroTrace 最高达到数百倍。对于这页图对应的 1 kB disk 场景，单线程 Bulkor 相比 Rust ZeroTrace 有 22.8 到 34.2 倍加速；16 线程时则达到 139.1 到 160.6 倍。

图中的柱状图不需要逐个读数，重点看趋势：随着数据规模增大，Bulkor 的优势更明显。这和它把复杂度从 O(N log^3 N) 降到 O(N log^2 N) 是一致的。

过渡句：最后结合论文内容，我总结一下它的贡献、不足和自己的思考。

## 第 12 页：贡献、不足与未来想法

建议时间：90 秒

核心句：这篇论文的价值不仅是优化一个算法，还提醒我们关注安全系统的初始化、恢复和布局转换阶段。

图示提示：按三栏讲：贡献、不足、未来想法。

口播稿：

我认为这篇论文的主要贡献有四点。第一，它系统定义了 ORAM bulk loading 问题，把 ORAM 初始化从一个工程细节变成了明确研究对象。第二，它指出简单 shuffle 并不安全，并解释了为什么 leaf label 分布必须和标准 Path ORAM 一致。第三，它提出 Bulkor，把理论复杂度降低到 O(N log^2 N)。第四，它在 SGX 环境中实现并验证了性能收益。

不足方面，我认为主要有三点。第一，实验主要围绕 Intel SGX，其他 TEE 环境还需要进一步验证。第二，oblivious sort，尤其是 bitonic sort，对超大规模数据仍然有较高常数开销。第三，论文的磁盘实验主要是单盘场景，现代 SSD 或 NVMe 场景下的性能瓶颈可能不同。

未来可以考虑三类方向：设计低常数的 doubly-oblivious sort；面向 SSD/NVMe 优化 bulk loading；以及把这种高效 ORAM 构建能力集成到安全数据库或查询优化器里。

我自己的理解是，安全系统不仅要关注正常访问阶段，还要关注初始化、恢复和布局转换这些容易被忽略的阶段。

过渡句：最后用三句话总结这篇论文。

## 第 13 页：总结

建议时间：50 秒

核心句：安全系统不仅要访问得安全，也要构建得安全、恢复得高效。

图示提示：逐条读三个 takeaway，最后停在结束句。

口播稿：

最后总结一下。第一，加密不能隐藏访问模式，ORAM 是解决访问模式泄漏的重要技术。第二，ORAM 初始化本身也可能成为安全系统的性能瓶颈，尤其在数据恢复、布局转换和安全查询处理中。第三，Bulkor 的核心思路是先随机分配 leaf label，再用 oblivious 的方式调整布局，从而实现安全高效的 Path ORAM bulk loading。

这篇论文给我的启发是：安全系统不仅要访问得安全，也要构建得安全、恢复得高效。我的汇报到这里结束，谢谢大家。
